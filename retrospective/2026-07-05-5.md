## Part 1 — what happened

### Phase 1 — orientation and scoping

The task: survey `ai-utils/coe` plus seven read-only sibling repos and suggest how to standardize and constrain their directory structures and documents. `coe/README.md` turned out to already define this work as its roadmap step 0 ("survey current projects… the output is a friction list, ranked"), which fixed the deliverable's shape before any repo was opened. A cheap structural scan of all eight repos (top-level `ls`, instruction-file inventory with line counts, `.claude/` and workflow listings) took a handful of shell commands and immediately surfaced the main axes: six different entry-file conventions, a set of skills copy-pasted across four or five repos, and root-directory hygiene ranging from 2 to 19 stray markdown files.

### Phase 2 — parallel survey fan-out plus drift measurement

Seven Explore subagents were dispatched in one message, one per read-only repo, each with an identical eight-heading brief (purpose / instruction chain / directory conventions / .claude layout / checks / knowledge flow / friction signals / distinctive ideas) plus one or two per-repo hints, and the standing instruction "be factual and specific; exact filenames and line counts; do not pad." While they ran, the orchestrator did the work that could not be delegated: a checksum drift pre-pass over the shared skills (two commands; headline result: `self-retrospective` exists in three simultaneous generations — 530, 1355, and 1401 lines — with the evidence-based amendment stranded in one repo), and a personal read of the two pivot documents, k8s-platform's `AGENTS.md` and `ai/LESSONS.md`. That direct read produced the survey's central finding: k8s-platform's forensics retired the exact rule-assembly pipeline the ai-skills registry is built around. All seven reports arrived with comparable structure; one subagent corrected a bad premise embedded in its brief ("~26 skills" → 24, counted from disk).

### Phase 3 — synthesis and deliverable

Before writing, the `human-scoped-deliverables` skill (installed in k8s-platform, not ai-utils) was loaded, and it materially reshaped the deliverable: a one-sitting synthesis (`coe/survey-2026-07-02.md`) split from an evidence companion (`coe/survey-2026-07-02-repo-profiles.md`); the rule-pipeline contradiction promoted to a labeled decision point with alternatives, trade-off, and rewind path; the recommendation marked as opinion; drift evidence rendered as tables; a method/epistemic note at the end. `coe/README.md` roadmap step 0 was marked done and linked.

### Phase 4 — ship

The `always-commit-skill-to-repo` skill was loaded before any git operation, per its mandatory trigger. One commit, push to the designated branch, ready-for-review PR #5 with a zero-context body, automatic subscription to PR activity, and an hourly self check-in armed (ai-utils has no CI, so review comments and merge state were the only signals to watch).

### Phase 5 — merge and retrospective (three days later)

The user returned with "merge then… perform a self-retrospective." PR #5 was squash-merged (matching the repo's existing one-commit-per-PR history) and the designated branch restarted from the merged main per the merged-PR rule. One genuine near-miss occurred here: the harness context said "today is 2026-07-05" while every container timestamp from the working session read 2026-07-02, and the initial conclusion was that the merged survey filenames were dated three days wrong. The skill's mandatory date verification plus one external cross-check (GitHub: PR #5 `created_at: 2026-07-02T15:28:24Z`) proved the opposite — the filenames were correct, the session simply spanned three days. A false "correction" of merged, linked filenames was avoided by one API call. The `self-retrospective` skill (software-factory copy, verified identical to `origin/main`) and its four templates were then read in full and this package authored from them.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory at `./2026-07-05-5/AGENTS-MD-<hash>-<kebab-name>.md` — that file carries the rule under a `# agent instruction` heading and the persuasion under a `# justification` heading. This Part 3 mirrors both inline.

An honest caveat the survey itself demands: ai-utils has no `AGENTS.md` today, which is exactly the "rules proposed into a repo with no agents file" failure the survey ranked as friction #1 in policy-engine. These four rules are therefore proposed as seed content for the AGENTS.md that COE v0.1 gives ai-utils — and per the checks-first doctrine (ADR draft below), each names its mechanical-check successor where one is plausible.

### Suggestion 1: Tool-verified dates outrank context-supplied dates — `AGENTS-MD-72082b1cb3`

- **Per-rule file**: [./2026-07-05-5/AGENTS-MD-72082b1cb3-tool-verified-dates-outrank-context-dates.md](./2026-07-05-5/AGENTS-MD-72082b1cb3-tool-verified-dates-outrank-context-dates.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Tool-verified dates outrank context-supplied dates.** Before writing any date into a filename or document, verify it with a tool call (`date -u`); when a harness-supplied date and the container clock disagree, resolve the conflict with an external timestamped record (e.g., GitHub `created_at`) and record the provenance rather than silently picking one.
>
> *Grounded in: the PR #5 survey-date false alarm resolved via GitHub timestamps (2026-07-05).*

**Justification** (verbatim from the per-rule file's `# justification` section):

During the COE survey session, the harness context block said "Today's date is 2026-07-05" while every file timestamp and the container clock read 2026-07-02. The agent initially concluded the survey filenames (`survey-2026-07-02.md`, already merged to main in PR #5) were dated three days wrong and drafted a defect finding plus a plan to flag the "wrong" names to the owner. One GitHub API call (`created_at: 2026-07-02T15:28:24Z` on PR #5) proved the filenames were correct — the session simply spanned three days, and the context-supplied date described the continuation, not the original work. The cost of not having this rule would have been a false defect report and possibly a rename churning merged, linked files; the cost of the rule is one tool call plus, in the rare conflict case, one API lookup. The asymmetry is stark: dates silently anchor audit trails (retrospective filenames, survey as-of claims, PR cross-references), and a wrong "correction" damages them more than the original ambiguity ever could.

### Suggestion 2: Verify premises in subagent briefs against the tree — `AGENTS-MD-1514ac018d`

- **Per-rule file**: [./2026-07-05-5/AGENTS-MD-1514ac018d-verify-subagent-brief-premises.md](./2026-07-05-5/AGENTS-MD-1514ac018d-verify-subagent-brief-premises.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Verify premises in subagent briefs against the tree.** Any count, filename, or structural claim embedded in a subagent brief must be verified with `ls`/`grep` before dispatch, or explicitly marked as unverified with an instruction to the subagent to check it; a false premise multiplies across every downstream agent.
>
> *Grounded in: the "~26 skills" brief error, corrected to 24 by the software-factory survey agent.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The software-factory survey brief stated the repo had "~26 skills" — a number read off the session's skill-list reminder, which double-lists skills that several repos install. The actual on-disk count was 24. The error was harmless only because the brief also instructed the subagent to report facts from disk with exact filenames, so the agent counted for itself and corrected the premise in its report. Had the brief instead asked the agent to "summarize each of the 26 skills," the fabricated count would have shaped the output — and in a seven-agent fan-out, a shared wrong premise repeats seven times before the orchestrator sees it once. k8s-platform's forensics recorded exactly this failure class at larger scale (one unverified constraint propagated into three plans and fourteen reviews). The marginal cost is one `ls | wc -l` per load-bearing claim at briefing time; the alternative is paying for the correction in every downstream artifact.

### Suggestion 3: Orchestrator reads pivot documents personally — `AGENTS-MD-9a96ef30a4`

- **Per-rule file**: [./2026-07-05-5/AGENTS-MD-9a96ef30a4-orchestrator-reads-pivot-documents.md](./2026-07-05-5/AGENTS-MD-9a96ef30a4-orchestrator-reads-pivot-documents.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Orchestrator reads pivot documents personally.** When fanning research out to subagents, identify the small set of documents the synthesis will hinge on and read them directly instead of relying on subagent summaries; delegate breadth, never the load-bearing depth.
>
> *Grounded in: reading k8s-platform's ai/LESSONS.md directly surfaced the doctrine contradiction that became the survey's central finding.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The COE survey dispatched seven explorer subagents for breadth, but the orchestrator read two documents in full itself: k8s-platform's `AGENTS.md` and `ai/LESSONS.md`. That direct read is what produced the survey's headline: the precise forensic claim (152 rule candidates → 51 adopted → zero behavior change; hook-covered bug classes at zero recurrence) directly contradicts the ai-skills registry's rule-assembly design — a contradiction that had to be stated exactly to be credible, down to the wording of the remedy protocol and the amendment date. The k8s-platform survey agent's summary covered the same file accurately but at one level of compression removed; a synthesis built only on that summary would have flattened the fleet's most consequential finding into "k8s-platform prefers checks over rules." The cost of the rule is reading two or three documents (a few hundred lines each) instead of zero. The cost of skipping it is a synthesis whose central claim the author has never actually seen — unverifiable at review time and fragile under challenge.

### Suggestion 4: Human-facing deliverables follow the human-scoped conventions — `AGENTS-MD-81b0e29f0b`

- **Per-rule file**: [./2026-07-05-5/AGENTS-MD-81b0e29f0b-human-facing-deliverables-conventions.md](./2026-07-05-5/AGENTS-MD-81b0e29f0b-human-facing-deliverables-conventions.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Human-facing deliverables follow the human-scoped conventions.** Any document whose primary audience is the human owner gets a short orientation block up top, the load-bearing finding first, comparison tables, labeled decision points with alternatives and rewind paths, opinion marked as opinion, and no hash IDs or cross-reference chains in body text.
>
> *Grounded in: loading human-scoped-deliverables before writing the PR #5 survey materially reshaped its structure.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The survey deliverable was drafted only after loading the `human-scoped-deliverables` skill (installed in k8s-platform and software-factory, not yet in ai-utils), and the skill changed the plan in concrete ways: the deliverable split into a one-sitting synthesis plus an evidence companion instead of one long report; the rule-pipeline contradiction was promoted from a friction-list entry to a labeled decision point with alternatives, a trade-off statement, and a rewind path; the recommendation was explicitly marked "opinion, not synthesis"; and the divergence evidence became tables rather than prose. The owner has stated plainly that database-normalized, cross-reference-heavy output is unreadable to a human, and that unreadable deliverables cost more than they save — if the reader has to re-ask, the writing failed. ai-utils has no AGENTS.md and no installed copy of that skill yet, so this rule carries the convention until COE distribution does; the marginal cost is following a checklist that already exists.
